# GitHub Copilot CLI transcript format: empirical inventory

Status: findings
Source: forty-four local session transcripts under `~/.copilot/session-state/`, all written by Copilot CLI 1.0.88 on 2026-09-25: eleven while the agentsummons `copilot` harness was being validated (plain replies, a preset-then-resumed session, `--available-tools` restriction, runs with and without `--allow-all`, a read-only `bash` call, a successful `create`, a run of repeated denied writes with model reasoning, two interactive sessions that only started and shut down, and one that hit the folder-trust prompt), seven from the drift probe (qa, shell, file, search with `--available-tools=glob,grep`, fetch, multi, with one retry), six `--model` runs to observe each provider family's reasoning shape (`gpt-5.6-terra`, `gpt-5.4`, `gemini-3.5-flash`, `grok-4.7`, `kimi-k3`, `mai-code-1.1-flash`; the GitHub "supported models" reference lists which models the CLI can use, and every family it lists was reachable on this Copilot Max account), five targeted probes for the shapes the first pass left unobserved (a `task` subagent, a `search_code_subagent`, `view` + `edit`, a background `bash` with `read_bash`/`list_bash`/`stop_bash`, a built-in GitHub MCP tool), and a third round closing the rest: every tool-error shape, an image viewed with `view`, background/nested/parallel/multi-turn subagents, a project skill, a custom agent (via `--agent` and via `task`), the `sql`/`session_store_sql`/`fetch_copilot_cli_documentation` tools, a user-configured stdio MCP server (`--additional-mcp-config`), four more models (`claude-opus-5.5`, `claude-haiku-4.5`, `gpt-6-sol`, `gemini-3.8-flash`), `--reasoning-effort high`, and a resume that switches models. The default model on this account was `claude-sonnet-5`. There is no model-listing command in headless mode: `--model` takes the lowercase, dot-separated form of the documented name (`grok-4.7`, `kimi-k3`, `mai-code-1.1-flash`), and a bad id exits before any request, leaving a session directory with no `events.jsonl`. Unverified parts are flagged below; loud failure covers the gaps. The event schema is observed only: GitHub documents the config directory (its "CLI config dir" reference), not the events file, and an upstream request to document the schema (github/copilot-cli#3551) has no answer.

## Headless invocation (as agentsummons assembles it)

```bash
copilot --allow-all --session-id "$UUID" --output-format json -p "prompt"
copilot --allow-all --resume="$UUID" --output-format json -p "prompt"
```

- The prompt is `-p`, last. `--allow-all` is agentsummons's `AutoApprove` (equal to `--yolo`). Without it a headless run still executes read-only tools, but every write is denied with "Permission denied and could not request permission from user" and the run still exits 0 (the `b203e559` session below is 59 lines of that).
- `--session-id` presets the UUID; if that UUID already exists it resumes instead of failing. `--resume=<id>` appends to the same session (observed: the events file grew from 9 to 18 lines, no new session directory).
- `--available-tools=a,b` restricts tools and also drops the built-in GitHub MCP server's tools. Built-in tool names registered on 1.0.88 (from `session.usage_checkpoint`'s tool list): `bash`, `read_bash`, `stop_bash`, `list_bash`, `view`, `create`, `edit`, `web_fetch`, `fetch_copilot_cli_documentation`, `search_code_subagent`, `skill`, `sql`, `session_store_sql`, `read_agent`, `list_agents`, `write_agent`, `grep`, `glob`, `task`, plus `github-mcp-server-*` MCP tools.
- Auto-update is on outside CI; pin with `COPILOT_AUTO_UPDATE=false`. Token auth: `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, or `GITHUB_TOKEN`.
- Stdout in JSON mode carries the same events as the file plus `"ephemeral": true` ones (message deltas, tool-call deltas, MCP status, `assistant.idle`) that are not persisted, and a final `{"type":"result","sessionId":...,"exitCode":...,"usage":{...}}` line that is stdout-only. `assistant.reasoning` and `tool.execution_partial_result` were seen on stdout and are not persisted on 1.0.88.

## File layout

Root: `~/.copilot/` (override: `COPILOT_HOME`). Per session:

```
~/.copilot/session-state/<session-uuid>/
  events.jsonl            the transcript (one JSON object per line)
  workspace.yaml          id, cwd, client_name, name (first prompt), user_named,
                          summary_count, fork_count, created_at, updated_at;
                          git_root/repository/host_type/branch when in a repo
  checkpoints/index.md    checkpoint table (empty header in every observed session)
  files/  research/       empty in every observed session
  rewind-file-snapshots/  tracking.json, plus index.json listing file pre/post images per user message once a write happened
  .workspace-fork.lock    only while a session is open
~/.copilot/session-state/.session-operation-locks/<session-uuid>.lock
~/.copilot/session-store.db (+ -wal/-shm)   SQLite index over the sessions
```

Sessions are keyed by UUID, not by working directory. The transcript records the cwd in-band (`session.start.data.context.cwd`), so a cwd filter is a scan over identities; `workspace.yaml` duplicates it out-of-band and is not consulted. The locator treats every regular file in a session directory other than `events.jsonl` as a sidecar, hidden directories under the root (`.session-operation-locks`) as bookkeeping, and files directly under the root as non-transcripts. A session directory without `events.jsonl` was not observed; the locator skips its files with a stable reason. One transcript per session: resumes append to the same file (a `session.resume` record marks the boundary), and there is no subagent file layout to discover (see known unknowns).

## Record envelope

Every line: `{"type": ..., "data": {...}, "id": "<uuid>", "timestamp": "<RFC3339 ms Z>", "parentId": "<uuid>|null"}`, exactly these five keys on every record of the main agent; records written by a subagent add a sixth, `agentId` (see finding 11), which becomes `Event.AgentID`. `parentId` is the previous record's `id` (null on the first), so the file is a chain rather than a set of independent records; line order is chain order in every observed file. `id`/`parentId` map onto `Event.ID`/`Event.ParentID`. Identity: `session.start.data.sessionId` (the directory name), `copilotVersion` (the harness version, once per file), `context.cwd`, and `context.branch` when the cwd is inside a git repository (with `gitRoot`, `repository`, `hostType`, `repositoryHost`, `headCommit`, `baseCommit`). The model is on each `assistant.message` (`data.model`) and in `session.model_change`.

## Structural findings

1. **One record per API message, nothing to fold.** `assistant.message` carries the complete text (`content`, empty string when the message was only tool requests), every tool request of the message (`toolRequests[]`, each with `toolCallId`, `name`, `arguments`, `type: "function"`, `intentionSummary`, `toolTitle`), and the reasoning. The adapter emits the message's `thinking` events, then its `tool_call` events, then the `assistant_message` anchor (no text block when `content` is empty), all sharing `MessageID` = `messageId`. `apiCallId` is the provider request id (`msg_...` on Anthropic).
2. **Tool calls are natively correlated.** `toolCallId` (`toolu_...` on Anthropic) links `toolRequests[]`, `tool.execution_start`, `permission.*`, and `tool.execution_complete`. `tool.execution_start` repeats the request's name and arguments and adds execution metadata (`shellToolInfo` on bash); it is preserved as a `system` event, not a second call, and it registers the tool name so a result whose request was never recorded still names its tool. Sequence inside a turn: `assistant.message` → `tool.execution_start` → (`permission.requested` → `permission.completed`) → `tool.execution_complete`, then `assistant.turn_end` and a new `assistant.turn_start` for the next API call; `turnId` counts API calls within an interaction (the `user.message`'s `interactionId`), restarting at "0" per user prompt.
3. **Results: what the model saw versus what the UI saw.** `result.content` is the model-visible text (bash appends `<shellId: N completed with exit code M>`); `result.detailedContent` (the diff for `create`, the numbered file for `view`) is UI-side and stays in the enrichment. Failures come in two shapes. A tool that could not run has `success: false`, no `result`, and `error{message, code}`: `code: "denied"` for a permission denial ("Permission denied and could not request permission from user") and `code: "failure"` for a tool's own failure (`view` "Path does not exist", `edit` "No match found", `web_fetch` "Error: Failed to fetch <url> - status code 404", with the status still in `toolTelemetry.metrics.httpStatusCode` and the URL in `restrictedProperties`). A shell command that exited nonzero is `success: true` with `shellExecution.exitCode` set and `toolTelemetry.properties.shell_error_category: "command_nonzero_exit"`; the model sees the stderr text plus the exit-code marker. The adapter marks both shapes `is_error` (the other adapters classify a nonzero exit the same way), feeds an `error.message` to the result content so a failed call's outcome is not empty, and still promotes a failed fetch's URL and status. Binary results: `view` on an image returns `result.content` "Viewed image file successfully." plus `result.binaryResultsForLlm[{type: "image", assetId, mimeType, byteLength, description}]`, and the bytes arrive one record earlier as `session.binary_asset` (base64 `data`) with the same `assetId`; the adapter appends an `image` content block holding the descriptor and keeps the asset record as a `system` event. Every other observed `result.content` is a string.
4. **Reasoning, per provider.** Copilot serves six model families on this account, but it records reasoning in only three shapes, keyed by the API the harness spoke (`session.usage_checkpoint` names it: `vendor` and `api_endpoint`):
   - Anthropic Messages (`claude-sonnet-5`; vendor `anthropic`, `/v1/messages`): `reasoningBlocks{provider: "anthropic-messages", blocks[{type: "thinking", thinking, signature}]}` plus the harness's flattened `reasoningText` (the same text, trailing whitespace trimmed) and `reasoningOpaque` (the same signature).
   - OpenAI Responses (`gpt-5.6-terra`, `gpt-5.4`, the `task` subagent's `gpt-5.6-luna`, and also xAI's `grok-4.7` and Microsoft's `mai-code-1.1-flash`; vendor `openai`, `/responses`): `reasoningBlocks{provider: "openai-responses", blocks[{type: "reasoning", id, content: [], summary: [{type: "summary_text", text}], encrypted_content; status ("completed", Grok only)}]}` plus `reasoningOpaque` (equal to the block `id`), `encryptedContent` (equal to the block's `encrypted_content`), and `reasoningText` (the joined summary) when a summary exists. `gpt-5.6-terra` and `mai-code-1.1-flash` produced empty summaries and no `reasoningText`; `gpt-5.4` and `grok-4.7` produced summaries. The thought itself is encrypted, like Codex's. Grok and MAI final messages also carry `serverTools{provider}`, and MAI's a `phase: "final_answer"`; both are additive keys the adapter leaves unread.
   - Flattened only (Google's `gemini-3.5-flash`, vendor `google`; Moonshot's `kimi-k3`, vendor `openai` over `/chat/completions`): no `reasoningBlocks`. Gemini records `reasoningText` (a summary) and `reasoningOpaque` (a ~5KB opaque blob); Kimi records `reasoningText` alone (the visible thought) and no opaque form.
   Within a family the shape holds (`claude-haiku-4.5` records thinking blocks, `gpt-6-sol` Responses blocks, `gemini-3.8-flash` the flattened pair), and a model can record no reasoning at all (`claude-opus-5.5` produced none). `--reasoning-effort high` changed nothing in the records (the effort is visible only as `reasoning_effort` inside `session.usage_checkpoint`). The adapter maps the provider-native blocks verbatim (one `thinking` event each): `thinking` blocks as text plus signature, `reasoning` blocks as the joined `content[]`/`summary[]` item texts plus `encrypted_content` as the signature. It falls back to the flattened pair when the blocks are absent (Gemini, Kimi), with an empty signature when there is no opaque form. Any other block type fails loudly. A `--model` run records the choice as `selectedModel` on `session.start` and writes no `session.model_change`; a resume with a different `--model` writes `session.model_change{source: "startup", previousModel, newModel}` after `session.resume`.
5. **System prompt is recorded per interaction.** `system.message` follows each `user.message` in a fresh process (8 of 10 prompts; the two resumed-turn prompts have none, the resumed process reuses its state), with `content` equal to `contentBlocks[0].content + "\n\n" + contentBlocks[1].content`: a static preamble (`isStatic: true`, ~5KB) and the dynamic part (version, model, environment, tool instructions, ~19KB). It is the vendor prompt, hence a synthetic stand-in in the fixture.
6. **User messages carry the user's own text.** `content` is the submitted prompt; `transformedContent` is what the model received, `<current_datetime>...</current_datetime>\n\n` + content. The adapter emits `content` (the wrapper is harness framing, recoverable via `KeepRaw`) and classifies every `user.message` as human: no harness-injected user-role record was observed, and the harness's own context lives in `system.message`. `parentAgentTaskId` is present on all ten and its meaning is unverified (a task id, presumably the subagent parent when applicable).
7. **Usage is session-cumulative, never per message.** `session.usage_checkpoint` (once per user prompt, after the interaction's last turn) records, per model, the *last* API call's `prompt_tokens`/`cache_read`/`cache_write` and no output tokens; the tool-loop calls before it are not itemized. `session.shutdown` records per-model cumulative `usage{inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens, reasoningTokens}` and `requests{count, cost}`, cumulative across resumes (the second shutdown of `2ec6dcd2` reports `count: 2` and the sum of both runs). Field semantics: `inputTokens` = `tokenDetails.input` + `cacheReadTokens` + `cacheWriteTokens` (the whole prompt; exact on every observed record: 2 + 0 + 20808 = 20810), so it is a `total_prompt_tokens` equivalent while `tokenDetails.input.tokenCount` is the Anthropic-style uncached remainder. The adapter attaches no usage to assistant messages (there is nothing per message to attach, and the schema's per-message `Usage` would be misrepresented by a session total), so `totals` is omitted; the numbers ride in the two records' `system` events. Promoting the shutdown totals is a candidate for a session-level usage surface or an opt-in transform, recorded in next-steps.
8. **Resume appends.** A resumed session continues the same file: `session.shutdown` → `session.resume` (with `eventCount` of the prior segment) → two `session.permissions_changed` (off, then on again under `--allow-all`) → `user.message`, then a fresh `interactionId` with `turnId` "0". No second `session.start`, no `system.message`.
9. **Sessions with no conversation** (interactive launches that exited, folder-trust prompts) are `session.start`, optional `session.model_change`/`session.info`, `session.shutdown` with `modelMetrics: {}` and no `currentModel`. `abort{reason: "user_initiated"}` closes an interaction whose turn produced no message.
10. **Search and fetch tools.** `glob` takes `{pattern}` and `grep` `{pattern, glob?}`; the drift probe observed the two requested in parallel in one `assistant.message` (`toolRequests` of length 2, each with its own `tool.execution_start`/`tool.execution_complete`), as did the multi probe's `bash` + `create` pair, so parallel calls are a real shape and not only a fixture construction. `web_fetch` takes `{url}`; its result content is `Contents of <url>:\n` followed by the page converted to markdown, and its `toolTelemetry` carries `restrictedProperties.url`, `metrics.httpStatusCode`, `metrics.originalContentLength` (a float; the converted content's length before truncation, not the resource size), `metrics.returnedContentLength`, `metrics.startIndex`, and `properties.raw` ("false" when converted). The adapter promotes the URL and status code to `tool_result.fetch`; `raw_bytes` stays unset because no pre-conversion size is recorded.
11. **Subagents live in the parent transcript, at any depth, in any number.** `task` (a general subagent: input `{name, agent_type, description, prompt}`) and `search_code_subagent` (a read-only search agent: input `{query, details}`) are ordinary `toolRequests`. Between the parent's `tool.execution_start` and `tool.execution_complete` for that call, the transcript interleaves the subagent's whole conversation, every record carrying an `agentId` envelope key (a fresh UUID for `task`; the parent's `toolCallId` itself for the search subagent) and, on its `assistant.message`/`tool.*` records, `data.parentToolCallId` (the parent's tool call). The bracket: `subagent.started` (toolCallId, agent name/type, resolved model, execution mode) → `subagent.configured` → (`subagent.selected` with the search agent's tool list) → `session.model_change` with `source: "agent"` → the subagent's `user.message` (the delegated prompt, `source: "agent-<parent session id>"`, `delivery` null for the search agent) → `system.message` → its turns → `subagent.completed` (for `task`: `totalToolCalls`, `totalTokens`, `durationMs`; the search agent reports none). The parent's `tool.execution_complete` carries the subagent's final text as `result.content`, `restrictedProperties.agent_id`, and `metrics.numberOfToolCallsMadeByAgent`; it was written before the subagent's last `assistant.turn_end` and `subagent.completed` in the `task` case and after them in the search case. The search subagent runs on a dedicated model (`copilot-search-a`) with a constrained toolset (`file_search {query}`, `grep_search {query, isRegexp, includePattern?}`, `read_file {filePath, startLine, endLine}`) whose results are plain strings (`N files found:`, `N matches` with `<match path= line=>` blocks, a fenced file listing) and empty `toolTelemetry`; it can issue eight requests in one message. The `task` subagent ran on `gpt-5.6-luna` (its agent definition's default), so a subagent's provider can differ from the parent's. Beyond the sync case: two `task` requests in one message run as two agents whose records interleave line by line (each with its own `agentId`; correlation is by `toolCallId`, so pairing survives the interleaving). `task` with `mode: "background"` records `executionMode: "background"`, returns immediately ("Agent started in background with agent_id: ..."), and the agent's turn runs while the parent continues; the parent then drives it with `list_agents {}` (a status table), `read_agent {agent_id, wait, timeout, since_turn?}` (the agent's turns as text), and `write_agent {agent_id, message}`, whose follow-up turn appears as another `user.message` under the same `agentId` with **no second `subagent.started`/`subagent.completed` bracket** (the first `subagent.completed` fired after turn one). `agent_type: "general-purpose"` is a second built-in agent type (`modelSelectionSource: "runtime_policy"`, resolved to `gpt-5.4`), and it can delegate again: the nested agent's `subagent.started` carries `parentId` (the delegating agent's `agentId`), its prompt's `source` is `agent-<parent agent id>`, and its `parentToolCallId` is the parent agent's tool call (OpenAI-style `call_...` ids when the delegating model is a GPT). A custom agent defined in `.github/agents/<name>.md` (loaded via `--add-dir`) is `agent_type: "<name>"` with `modelSelectionSource: "session_inheritance"`, a `subagent.selected` listing its `tools`, and telemetry `agent_type: "custom-agent"`; running the whole session as that agent (`--agent <name>`) writes a `subagent.selected` on the **main** agent (no `agentId`) and nothing else changes. The adapter parses subagent records as ordinary events stamped with `Event.AgentID`, classifies the delegated prompt as harness-origin (the `agent-` source prefix), and preserves the `subagent.*` records as `system` events; there is no subagent file layout, so the locator yields no `SubagentPaths` and `Meta.IsSubagent` is never set.
12. **Skills and the remaining tools.** `skill {skill}` loads a SKILL.md (project `.github/skills/<name>/`, personal `~/.copilot/skills/`, or plugin): the result is a one-line confirmation (telemetry `skillSource`, `skillNameHash`), followed by `skill.invoked` (the skill's full content, path, description, trigger) and `skill.context_delivered_ref` (the `<skill-context>` wrapper and a content hash for what was injected into the model's context; the wrapper names the skill's base directory and lists every file under the skill directory, so the model learns of bundled files the body never mentions). Activating the same skill again with its body unchanged (a `--resume` turn, or the same session) logs `skill.invoked_ref` (content hash and length, no body) plus a fresh delivery record with the same hash: the delivery repeats, the log stores the body once. `sql {query}` and `session_store_sql {query}` return markdown tables (telemetry `queryType`, `rowsReturned`; the latter `database: "session_store"`). `fetch_copilot_cli_documentation {query}` returns the CLI's README/help text. A user-configured MCP server (`~/.copilot/mcp-config.json`, `.mcp.json`, or `--additional-mcp-config`) exposes tools named `<server>-<tool>` with `mcpConfigSource: "user"` and `mcpTransport: "stdio"` on `tool.execution_start`; those names are user vocabulary, so a new server reads as tool-name drift in `drift scan` (only the built-in `github-mcp-server-*` prefix is collapsed). Remaining tools. `view {path}` returns the file text with a numbered `detailedContent` (telemetry `viewType`); `edit {path, old_str, new_str}` returns a one-line confirmation with the diff in `detailedContent` (telemetry `codeBlocks`, `linesAdded`/`linesRemoved`, `restrictedProperties.filePaths`); `bash` with `mode: "async"` and `initial_wait` returns `<command started in background with shellId: N>` with no `shellExecution`; `read_bash {shellId, delay}` returns the output plus the completion marker and a `shellExecution.exitCode`; `list_bash {}` returns a shell table; `stop_bash {shellId}` returns `<command with id: N stopped>`. Built-in MCP tools are named `github-mcp-server-<tool>`; their `tool.execution_start` adds `mcpServerName`, `mcpConfigServerName`, `mcpTransport` ("http"), `mcpConfigSource` ("builtin"), and `mcpToolName`, and the result telemetry carries `metrics.mcp_result_content_bytes`. All results observed are strings.
13. **Timestamps** are RFC 3339 UTC with milliseconds on every record. `session.start.data.startTime` matches the record timestamp to within tens of ms; `sessionStartTime` in shutdown is the same instant as epoch milliseconds.

## Known unknowns (revisit with more transcripts)

- **Detached subagents.** `resumable: true` (a subagent surviving the session) is unobserved; depth-two nesting, background mode, parallel agents, and multi-turn agents are covered (finding 11).
- **Non-image binary assets.** `session.binary_asset.type` other than `"image"` (documents, audio) is unobserved; the adapter maps unknown types to `other` blocks.
- **Other providers.** Every model family the GitHub supported-models reference lists for the CLI is observed (finding 4: Anthropic, OpenAI, Google, xAI, Moonshot, Microsoft), and they reduce to three recorded shapes. A block type other than `thinking`/`reasoning` fails loudly. An OpenAI-style block's `content[]` items were empty in every observed case (only `summary[]` carried text); their assumed `{type, text}` shape is the Responses API's. Claude Opus and Haiku, the other GPT sizes, and the newer Gemini Flash releases were not run; they share their families' APIs.
- **Unexercised tools.** None of the built-in tool names registered on 1.0.88 remains unobserved. Tool kinds are mapped for the file, shell, search, fetch, and agent-reading tools; everything else is `other`.
- **Non-string `result.content`** (images, structured MCP results) is unobserved; preserved as an `other` block if it appears.
- **`user.message.delivery`** values other than `"idle"` and `null` (steering, queued input) are interactive-only and unobserved. The only harness-authored user-role content is a subagent's prompt (classified by its `source`).
- **API errors and retries.** No provider error or retry was observed in any session; their shape, if recorded at all, is unknown.
- **Stdout-only types** (`assistant.reasoning`, `tool.execution_partial_result`, `assistant.idle`, the `result` line) were not persisted on 1.0.88; if a later release persists them under the conversation namespaces they fail loudly by design.
- **Compaction/summaries.** `workspace.yaml` has `summary_count` and `fork_count`; the corresponding records were not observed.
